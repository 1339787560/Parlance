# 数据迁移产品设计 — chunkSvr → CP（在线懒迁移）

> 迁移范围：金币（积分补偿）、荣耀特权等级与奖励领取记录、周月卡时间、迎新礼包剩余签到数据
> 触发时机：玩家登录（OnLogon），所有玩家均执行特权迁移；积分补偿仅限有局数的玩家

***

## 一、迁移流程总览

```
玩家登录 → CP OnLogon 回调
  → 进入 convert 模块回调
  → 检查迁移标记（位掩码），确定哪些模块未迁移
  → 积分补偿（score < 0 的玩家）：
      检查 bit 3 未迁移 → async_sendGoldCoin_super 发放 |score| 积分抵消负数 → 置位 bit 3
  → 金币迁移（仅对有局数 bout ≥ 1 的玩家）：
      检查 bit 4 未迁移 → HTTP 拉取 newdeposit → async_sendGoldCoin_super 发放等量积分 → 置位 bit 4
  → 对每个未迁移模块，依次执行：
      ① convert 模块 HTTP POST chunkSvr /v1.0/chunkluareq，拉取该模块数据
      ② 数据格式转换（chunkSvr JSON → CP 数据结构）
      ③ convert 模块将迁移数据递交给目标模块（async_internal_call）
      ④ 目标模块处理完毕，返回处理结果给 convert 模块
      ⑤ 成功 → convert 模块置位该模块的迁移标记位
      ⑤ 失败 → 不置位，下次登录重试该模块
  → 迁移标记双写（Redis + MySQL）
  → convert 模块处理完所有模块后，返回处理结果给客户端
```

### 迁移标记位定义

| 位     | 模块                          | 标记含义           |
| ----- | --------------------------- | -------------- |
| bit 0 | 荣耀特权 (TQVip)                | VIP 等级与奖励记录已迁移 |
| bit 1 | 周月卡 (TQMonthCard)           | 月卡/周卡时间已迁移     |
| bit 2 | 迎新礼包 (TQNewPlayerDailyGift) | 签到剩余数据已迁移      |
| bit 3 | 积分补偿 (NewDeposit)            | 负积分已补偿         |
| bit 4 | 金币迁移 (GoldCoin)              | 金币→积分已发放      |

- 标记值存储为整数，如 `0b11111 = 31` 表示全部迁移完成
- 部分迁移：如 `0b01111 = 15` 表示特权/月卡/礼包/积分补偿已迁移，金币未迁移
- 0 = 未迁移任何模块，下次登录全量重试
- 积分补偿和金币迁移各自独立标记，不会因一方失败影响另一方
- 积分补偿仅当 `score < 0` 时执行；`score ≥ 0` 直接置位 bit 3（跳过视为"已完成"）
- 金币迁移仅当 `bout ≥ 1` 时执行；无局数玩家直接置位 bit 4（跳过视为"已完成"）

**位掩码优势**：某模块迁移失败不影响其他模块，下次登录只重试失败模块，避免重复拉取已成功数据。

## 二、数据映射关系

### 2.1 积分补偿 → 金币迁移

积分补偿与金币迁移分为两步，均由 convert 模块直接管理，独立标记、独立重试。

#### 2.1.1 积分补偿

| 数据来源 | 返回字段 | CP 目标 | 转换要点 |
|---------|---------|--------|---------|
| `logon.usergameinfo.score` | `score` | leveldefine 积分（通过 `async_sendGoldCoin_super` 发放） | 仅 score < 0 时发放 \|score\| 抵消负数 |

**积分补偿规则**：

- 数据来源：OnLogon 回调参数 `logon.usergameinfo.score`，不依赖 chunkSvr HTTP
- 仅当 `score < 0` 时执行：发放 `|score|` 等量积分，使积分归零
- `score ≥ 0` 时直接置位 bit 3（跳过，视为"已完成"）
- 使用 `async_sendGoldCoin_super` 发放（分批发放，每批 ≤ 2,000,000,000）
- 发放失败（返回 false）→ 不置位 bit 3 → 下次登录重试

#### 2.1.2 金币迁移

| chunkSvr 接口 | 返回字段 | CP 目标 | 转换要点 |
|-------------|---------|--------|---------|
| `querynewdeposit` | `nUserID`, `newdeposit` | leveldefine 积分（通过 `async_sendGoldCoin_super` 发放） | Lua 金币 = Creator 积分；大额分批发放（≤2B/批） |

**金币迁移规则**：

- Lua 版本金币 等于 Creator 版本积分
- 金币迁移时发放等量积分，使用 `async_sendGoldCoin_super`（分批发放，每批 ≤ 2,000,000,000）
- 线上存在数千位 newdeposit > 2,147,483,647 的玩家，`async_sendGoldCoin_super` 通过 `Math.ceil(goldCoinNum / 2B)` 自动拆分为多批次，每批调用 `async_batch_send_reward` 发放
- 仅当 `bout ≥ 1` 时执行；无局数玩家直接置位 bit 4
- 发放失败（返回 false）→ 不置位 bit 4 → 下次登录重试

### 2.2 荣耀特权 → leveldefine

| chunkSvr 接口  | 返回字段                                                                                                         | CP 目标模块     | CP 数据结构                    | 转换要点    |
| ------------ | ------------------------------------------------------------------------------------------------------------ | ----------- | -------------------------- | ------- |
| `querytqvip` | `nUserID`, `grade`, `experience`, `maxgrade`, `maxexperience`, `rewardstatus`, `datetag`, `lastshowanigrade` | leveldefine | `UserData_PlayerLevelInfo` | 见下方字段映射 |

**字段映射规则**（等级机制变更）：

chunkSvr 原为充值通宝获得经验，CP 改为消耗通宝获得经验。因此迁移时：

| chunkSvr 字段                 | → CP 字段                         | 转换说明                   |
| --------------------------- | ------------------------------- | ---------------------- |
| `grade`                     | `userGrade`（通过 PlayerLevelData） | 直接映射，等级以 Lua 端数据为准     |
| `experience`                | `totalConsumeNum`               | 经验值转为消耗量               |
| `experience`                | `totalAcquireNum`               | 与 totalConsumeNum 保持一致 |
| `rewardstatus`              | `oneOffRewardStatusArray`       | 领奖记录以 Lua 端数据为准        |
| `lastshowanigrade`          | 忽略                              | CP 无对应字段               |
| `maxgrade`, `maxexperience` | 忽略                              | 由 CP 配置决定              |
| `datetag`                   | 忽略                              | CP 无对应字段               |

**rewardstatus 转换细节**（已对齐）：

chunkSvr rewardstatus 格式（实测玩家 1169648）：

```json
{"rewardstatus": [0,0,1,0,0,0,0,0,0]}
```

PB `repeated int32` → Lua 1 基整数键表。空表 `{}` 表示无领取记录。

**索引语义**：Lua `rewardstatus[i]` 对应等级 `i-1`（1 基 → 0 基等级）。长度动态，仅到当前 maxgrade+1。

**值语义**：`0` = 未领取，`1` = 已领取。

CP `oneOffRewardStatusArray` 格式：

```typescript
{ status: number, gotTime: number }[]  // 0 基，索引=等级
// status: 0=未领取(NOT_RECEIVED), 1=可领取(CAN_RECEIVED), 2=已领取(RECEIVED)
// gotTime: 领取时间戳（秒）
```

**转换规则**（简化：迁移只填 0 和 2，CAN_RECEIVED 由 CP 升级流程自动填充）：

| chunkSvr 值 | → CP status | → CP gotTime                | 说明                              |
| --------- | ----------- | ---------------- ----------- | ------------------------------ |
| `0`       | `0`         | `0`                         | 未领取                            |
| `1`       | `2`         | 迁移时间戳（`Date.now()/1000`） | Lua 1=已领取 → CP 2=RECEIVED     |

**索引偏移**：`rewardstatus[grade+1] → oneOffRewardStatusArray[grade]`，Lua 1 基索引减 1。

**数组长度**：CP 固定 `totalGradeCount`(16)，不足补 `{status:0, gotTime:0}`。

**CAN_RECEIVED(1) 自动填充**：迁移写入后，leveldefine 模块仿照升级流程执行 `updateRewardList()`，自动判断哪些等级奖励应设为 CAN_RECEIVED(1)。迁移脚本无需手动计算可领取状态。

### 2.3 周月卡 → cmmonthcard

| chunkSvr 接口        | 返回字段                                                        | CP 目标模块     | CP 数据结构            | 转换要点                                   |
| ------------------ | ----------------------------------------------------------- | ----------- | ------------------ | -------------------------------------- |
| `querytqmonthcard` | `nUserID`, `monthcard`, `weekcard`, `datetag`, `redress`    | cmmonthcard | `CMMONTHCARD_INFO` | starttime → BuyTime; endtime → EndTime; redress → redressUseTime |

chunkSvr 返回格式（实测）：

```json
{
  "weekcard": {"starttime": 20260518103510, "endtime": 20260726103510, "datetag": 20260518},
  "monthcard": {"starttime": 20260518103508, "endtime": 20260726103508, "datetag": 20260518}
}
```

CP `_CARD_INFO` 字段：

```typescript
BuyTime: number;   // 秒级时间戳
EndTime: number;   // 秒级时间戳
type: CARD_TYPE;   // month=1, week=2
```

**转换要点**：

- chunkSvr starttime/endtime 是 `YYYYMMDDHHmmSS` 格式的整数（如 20260518103508），CP BuyTime/EndTime 是秒级时间戳
- **已过期的周月卡**：仅迁移上次的 starttime、endtime，CP 侧按 EndTime 判断过期

**包赔数据调查结论**（已对齐）：

包赔数据存储在 **TQProp 道具缓存**（非月卡缓存），通过两个专用道具 ID 查询：`MONTHCARDMIANPEIKA` 和 `WEEKCARDMIANPEIKA`。每个道具含 `baopeikainfo` 子对象：

```typescript
baopeikainfo: {
    gettime: number;   // 包赔道具发放时间
    endtime: number;   // 包赔有效期截止
    datetag: number;   // 上次包赔领取日期（YYYYMMDD）
    opcount: number;   // 每日包赔次数上限（配置值）
}
```

CP 侧 `redressUseTime` 为单个 `number` 字段，格式 YYYYMMDD，语义为"上次包赔领取日期"。

**转换规则**：`baopeikainfo.datetag → redressUseTime`（同为 YYYYMMDD 格式，直拷）。无包赔道具时 `redressUseTime = 0`。

**HTTP 接口需扩展**：`querytqmonthcard` handler 需追加查询 TQProp 缓存，提取 `MONTHCARDMIANPEIKA`/`WEEKCARDMIANPEIKA` 的 `baopeikainfo.datetag`，合并到响应的 `redress` 字段。

### 2.4 迎新礼包 → cmnewplayerdailygift

| chunkSvr 接口               | 返回字段                                                                                         | CP 目标模块              | CP 数据结构                           | 转换要点      |
| ------------------------- | -------------------------------------------------------------------------------------------- | -------------------- | --------------------------------- | --------- |
| `querynewplayerdailygift` | `nUserID`, `newplayer`, `triggerdate`, `lastdate`, `receivedays`, `remaindays`, `awarditems` | cmnewplayerdailygift | `UserData_NewPlayerDailyGiftInfo` | 见下方迁移判断逻辑 |

chunkSvr 返回格式（实测玩家 1169648）：

```json
{
  "newplayer": 1,
  "remaindays": 7,
  "triggerdate": 20260420,
  "lastdate": 0,
  "receivedays": 3,
  "awarditems": [1000000, 2000000, 3000000, 4000000, 5000000, 6000000, 7000000]
}
```

CP 数据结构：

```typescript
buyTime: number;          // 秒级时间戳
lastClaimDay: number;     // 已领取到第几天 (0-6)
lastClaimDate: number;    // 上次领取日期（YYYYMMDD）
```

**迁移判断逻辑**（按购买日期判断签到有效期）：

| 条件                                 | 处理                        | bit 2                |
| ---------------------------------- | ------------------------- | -------------------- |
| 未充值（newplayer=0）                   | CP 端允许玩家继续充值，不写入礼包数据      | 置位（视为已迁移，CP 端按新用户处理） |
| 已充值且已过期（购买日期 + checkindays < 当前日期） | CP 端迎新礼包视为已迁移完毕，不写入签到数据   | 置位                   |
| 已充值且未过期（购买日期 + checkindays ≥ 当前日期） | 迁移签到数据，让玩家能继续在 CP 端领取剩余奖励 | 置位（写入成功后）            |

**字段语义对齐**（已对齐）：

| chunkSvr 字段    | 语义               | CP 字段          | 语义               | 转换规则                    |
| -------------- | ---------------- | -------------- | ---------------- | ----------------------- |
| `receivedays`  | 已领取次数（0-7）       | `lastClaimDay` | 已领取次数（0-6）       | 直拷（语义完全等价，都是已领取天数计数）    |
| `triggerdate`  | 触发/购买日期（YYYYMMDD） | `buyTime`      | 购买时间（秒级时间戳）      | `YYYYMMDD → epoch` 格式转换 |
| `lastdate`     | 上次领取日期（YYYYMMDD） | `lastClaimDate`| 上次领取日期（YYYYMMDD） | 直拷（格式相同）                |
| `remaindays`   | 剩余可领取天数         | —              | CP 从 buyTime 动态计算 | 丢弃，不迁移                  |
| `awarditems`   | 7天奖励列表          | —              | CP 从配置读取          | 丢弃，不迁移（配置数据非用户数据）       |
| `newplayer`    | 是否已充值（0/1）      | —              | CP 从 buyTime 推断   | 用于迁移判断，不直接映射            |

**receivedays ↔ lastClaimDay 对齐说明**：

两边语义完全等价——都是"已领取奖励的天数"。初始值为 0，每次领取 +1。唯一行为差异：CP 在充值时自动发放第 1 天奖励并设 lastClaimDay=1，chunkSvr 需玩家手动领取第 1 天。但存储值含义相同，可直拷。

**签到有效期判断**：用 `checkindays` 配置项 + `triggerdate` 计算，不用 `remaindays` 字段。判断条件：`当前日期 - triggerdate < checkindays`。

## 三、积分补偿与金币迁移逻辑

### 3.1 积分补偿（bit 3）

#### 触发条件

- 玩家积分 < 0（`logon.usergameinfo.score < 0`）
- 积分补偿（bit 3）未标记

#### 执行步骤

1. 读取 `logon.usergameinfo.score`
2. `async_sendGoldCoin_super` 发放 `|score|` 积分（抵消负数）
3. 发放成功 → 置位 bit 3，双写迁移标记

#### 降级策略

| 场景 | 处理 |
|------|------|
| `score ≥ 0` | 直接置位 bit 3，跳过 |
| `async_sendGoldCoin_super` 返回 false | 不置位 bit 3，下次登录重试 |

> 积分补偿幂等：发放 `|score|` 使积分归零。重复发放会导致积分偏正，但 bit 3 不置位则下次重试——实际上只要首次成功就置位，不会重复。

### 3.2 金币迁移（bit 4）

#### 触发条件

- 玩家有局数（`bout ≥ 1`）
- 金币迁移（bit 4）未标记

#### 执行步骤

1. HTTP POST chunkSvr `querynewdeposit`，拉取 newdeposit
2. `async_sendGoldCoin_super` 发放等量积分（newdeposit 值）
3. 发放成功 → 置位 bit 4，双写迁移标记

#### 降级策略

| 场景 | 处理 |
|------|------|
| 无局数（bout = 0） | 直接置位 bit 4，跳过 |
| chunkSvr 不可达 | 不置位 bit 4，下次登录重试 |
| chunkSvr 返回 `err` 非 null | 不置位 bit 4，下次重试 |
| chunkSvr 返回 newdeposit=0 | 置位 bit 4（发放 0 积分，视为已迁移） |
| `async_sendGoldCoin_super` 返回 false | 不置位 bit 4，下次重试 |

> **无局数玩家**：直接置位 bit 4，跳过金币迁移。
>
> **执行顺序**：积分补偿（bit 3）先行，金币迁移（bit 4）随后。两者独立标记，互不影响。

## 四、chunkSvr HTTP 接口规格

chunkSvr 已完成 HTTP 查询接口部署（msgcenterversion=843 热更生效）。

| 接口名                       | 请求                                                | 返回字段                                                                                                       |
| ------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `querynewdeposit`         | `{"req":"querynewdeposit","nUserID":xxx}`         | `nUserID, newdeposit`                                                                                      |
| `querytqvip`              | `{"req":"querytqvip","nUserID":xxx}`              | `nUserID, grade, experience, maxgrade, maxexperience, rewardstatus, datetag, lastshowanigrade`             |
| `querytqmonthcard`        | `{"req":"querytqmonthcard","nUserID":xxx}`        | `nUserID, monthcard{starttime,endtime,datetag}, weekcard{starttime,endtime,datetag}, monthcardRedress?, weekcardRedress?` |
| `querynewplayerdailygift` | `{"req":"querynewplayerdailygift","nUserID":xxx}` | `nUserID, newplayer, triggerdate, lastdate, receivedays, remaindays, awarditems`                           |

**包赔字段说明**：`monthcardRedress` / `weekcardRedress` 为可选字段，仅在玩家拥有免赔道具(propid 20002/20003)时出现。格式：

```json
{"monthcardRedress": {"datetag": 20260518, "gettime": timenum, "endtime": timenum}}
```

HTTP 端点：`POST http://{chunkSvrIP}:9080/v1.0/chunkluareq`

响应统一格式：

```json
{"err": null, "ret": "{...JSON字符串...}"}
```

- `err` 为 null 表示成功，`ret` 为内层 JSON 字符串需二次解析
- `err` 非 null 表示 Lua 执行异常

不存在用户返回默认值（零值/空表），不报错。

**HTTP 超时**：2 秒。chunkSvr 本地请求平均 <5ms，2 秒已覆盖极端场景。

**单线程并发能力**（实测）：

| 并发 | RPS  | 平均响应   | P50   |
| -- | ---- | ------ | ----- |
| 1  | 591  | 1.6ms  | -     |
| 10 | 1937 | 2.9ms  | 3ms   |
| 20 | 344  | 21.8ms | 6.7ms |

登录场景并发 <10 人/秒，单线程完全够用。

## 五、迁移标记机制

| 属性        | 说明                                |
| --------- | --------------------------------- |
| 标记位置      | Redis + MySQL 双写                  |
| Redis key | `xzmp_chunksvr_migrated:{userid}` |
| MySQL 表   | 复用现有 CP 用户数据表（CP 只有一个表可用）         |
| 标记方式      | SET，值为位掩码整数（0-31）                 |
| 过期时间      | 永久保留                              |
| 检查时机      | OnLogon 回调开头，按位判断各模块是否已迁移         |

**位掩码读写示例**：

```
读取: flags = GET xzmp_chunksvr_migrated:{uid}  (nil → 0)
判断: if (flags & 0x01) == 0 then TQVip 未迁移 end
置位: flags = flags | 0x01  → SET xzmp_chunksvr_migrated:{uid} flags
全量完成: flags == 0x1F (31)
```

**双写保证**：迁移标记是重要信息，Redis 和 MySQL 均写入。Redis 优先检查（快），MySQL 作为持久备份（Redis 丢失时可恢复）。每次置位操作同时写入两处。

## 六、降级策略

| 异常场景                             | 处理                            |
| -------------------------------- | ----------------------------- |
| chunkSvr 不可达（HTTP 超时 >2s / 连接失败） | 金币迁移模块不置位标记，下次登录重试；其他模块仍尝试       |
| chunkSvr 返回 `err` 非 null         | 同上，不置位，下次重试                   |
| chunkSvr 返回数据为空（默认值）             | 置位标记（视为已迁移空数据），避免反复拉取         |
| 某模块 async\_internal\_call 写入失败   | 不置位该模块标记，下次重试；不影响其他模块         |
| `async_sendGoldCoin_super` 发放失败  | 不置位对应标记（bit 3 或 bit 4），下次重试 |

**位掩码保证鲁棒性**：单模块失败不影响其他模块标记，下次登录只重试失败模块。即使多次登录部分模块反复失败，已成功的模块不会重复拉取和写入。

**chunkSvr 长期不下线**：迁移无时间压力，失败玩家可持续重试直到完成。

| 模块                   | MySQL 表                                                                   | Redis Key                                                                                     | 数据序列化 |
| -------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----- |
