# 迁移结果推送消息文档

## 消息名

`migrationResult_convert_xzmp`

## 触发时机

玩家登录时，`convert_xzmp` 执行数据迁移完成后，主动推送给客户端。

## 消息体

```typescript
{
    flags: number;               // 迁移标记位掩码 (0-31)
    levelInfo: LevelInfo | null;
    monthCardInfo: MonthCardInfo | null;
    giftInfo: GiftInfo | null;
}
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `flags` | `number` | 当前迁移标记位掩码。`0x1F (31)` = 全部迁移完成。客户端无需关心具体位含义，仅用于调试 |
| `levelInfo` | `LevelInfo \| null` | 荣耀特权迁移数据。`null` = 本次未迁移（已迁移或失败） |
| `monthCardInfo` | `MonthCardInfo \| null` | 月卡迁移数据。`null` = 本次未迁移 |
| `giftInfo` | `GiftInfo \| null` | 迎新礼包迁移数据。`null` = 本次未迁移 |

### LevelInfo（荣耀特权 — 原始存储格式）

```typescript
{
    totalAcquireNum: number;                              // 累计获得通宝量（= 迁移前 experience）
    totalConsumeNum: number;                              // 累计消耗通宝量（= 迁移前 experience）
    lastAcquireTime: number | string;                     // 上次充值时间（秒级时间戳）
    lastConsumeTime: number | string;                     // 上次消耗时间（秒级时间戳）
    lastLogonTime: number | string;                       // 上次登录时间（秒级时间戳）
    userDegradeNum: number;                               // 降级次数
    oneOffRewardStatusArray: {                             // 一次性奖励状态，固定 16 项
        status: number;    // 0=未领取, 1=可领取, 2=已领取
        gotTime: number;   // 领取时间戳（秒），未领取=0
    }[];
}
```

### MonthCardInfo（月卡 — 原始存储格式）

```typescript
{
    monthCardInfo: {
        BuyTime: number;    // 购买时间（YYYYMMDDHHmmSS 格式的整数）
        EndTime: number;    // 到期时间（YYYYMMDDHHmmSS 格式的整数）
        type: 1;            // 月卡类型固定为 1
    } | null;               // null = 无月卡数据
    weekCardInfo: {
        BuyTime: number;    // 购买时间（YYYYMMDDHHmmSS 格式的整数）
        EndTime: number;    // 到期时间（YYYYMMDDHHmmSS 格式的整数）
        type: 2;            // 周卡类型固定为 2
    } | null;               // null = 无周卡数据
    redressUseTime: number; // 上次包赔领取日期（YYYYMMDD 格式），0=无包赔
}
```

### GiftInfo（迎新礼包 — 原始存储格式）

```typescript
{
    buyTime: number;        // 购买时间（秒级时间戳）
    lastClaimDay: number;   // 已领取天数（0-N）
    lastClaimDate: number;  // 上次领取日期（YYYYMMDD 格式），0=未领取过
}
```

## 与查询接口的数据差异

**迁移推送的是原始存储格式，不是客户端查询接口返回的加工后格式。** 对比：

| 模块 | 迁移推送（原始） | 查询接口（加工后） | 差异 |
|------|---------------|----------------|------|
| 荣耀特权 | `totalConsumeNum`, `totalAcquireNum`, `oneOffRewardStatusArray`, ... | `userGrade`, `curExp`, `toNextLevelPayDiff`, `userDegradeNum`, `oneOffRewardStatusArray` | 推送无 `userGrade`/`curExp`/`toNextLevelPayDiff`，需从 `totalConsumeNum` 查配置计算 |
| 月卡 | `monthCardInfo{BuyTime,EndTime,type}`, `weekCardInfo{...}`, `redressUseTime` | `monthEndTime`, `weekEndTime` | 推送含完整购买时间+包赔数据，查询接口只返回有效到期时间 |
| 礼包 | `buyTime`, `lastClaimDay`, `lastClaimDate` | `hasPurchased`, `buyTime`, `lastClaimDay`, `canClaimToday`, `remainingDays` | 推送无 `canClaimToday`/`remainingDays`，需本地计算 |

## 客户端处理建议

### 方案 A：收到推送后重新查询（推荐）

收到 `migrationResult_convert_xzmp` 后，对非 null 的模块发起对应查询请求，用查询结果刷新 UI：

```
收到 migrationResult_convert_xzmp
  → if levelInfo != null:  发送 QUERY_LEVELDEFINE_CONFIG
  → if monthCardInfo != null:  发送 QUERY_CMMONTHCARD_CONFIG
  → if giftInfo != null:  发送 QUERY_NEWPLAYERDAILYGIFT_CONFIG
```

优点：数据格式与现有逻辑完全一致，无需额外解析。
缺点：多一次网络请求。

### 方案 B：直接用推送数据刷新

客户端理解原始格式并自行计算派生字段：

- **levelInfo**：用 `totalConsumeNum` 查等级配置表算出 `userGrade`；`oneOffRewardStatusArray` 可直接使用
- **monthCardInfo**：比较 `EndTime` 与当前时间判断是否有效；`BuyTime` 格式为 `YYYYMMDDHHmmSS` 整数
- **giftInfo**：用 `buyTime` + 配置 `checkindays` 计算过期状态和 `remainingDays`；比较 `lastClaimDate` 与当前日期计算 `canClaimToday`

优点：零延迟刷新。
缺点：客户端需重复服务端计算逻辑，且需维护两套数据解析。

### 推荐：方案 A

迁移只发生一次（登录时），额外查询的延迟可忽略。方案 A 零维护成本，数据一致性有保障。
