# 对局抽奖

## 1. 文档信息剩余局数

- 功能名称：对局抽奖
- 文档目的：统一玩法规则、配置口径、埋点口径与上线验收标准

***

## 2. 功能目标

### 2.1 业务目标

1. 重做“对局抽奖”系统，关联房间对局。
2. 建立“完成对局 -> 获得抽奖机会 -> 抽取奖励”的稳定激励闭环。
3. 通过场次分层，提升中高场玩家对局积极性与留存。
4. 在不破坏经济系统的前提下，提升活跃与付费协同效率。

### 2.2 玩家价值

- 新手玩家：快速形成"打一把就有奖"的正反馈。
- 中层玩家：稳定体验"打局-领奖"节奏，提升日常黏性。
- 高层玩家：高场次独占奖励提升对局动机与身份感。

### 4.2 抽奖券及任务机制

#### 4.2.1 进度与次数规则（分场次 · 多阶段 · 末段循环）

**总原则：** R1\~R5 **五个场次档位各自一套完整配置**（任务阶段列表 + 奖池引用 + 当日上限等），互不串联。每个场次内支持 **A / B / C / D …** 多个任务阶段（数量由配表决定）；须**完成前置阶段任务**后才解锁下一阶段；当玩家处于**配置中的最后一个阶段**时，之后当日永久**循环使用最后一个阶段的** `**targetWins**` **与绑定的奖池概率**。

| 规则   | 前置条件                                         | 行为                   | 结果                                                      |
| ---- | -------------------------------------------- | -------------------- | ------------------------------------------------------- |
| 进度累加 | 玩家在对应等级银子房间完成一局对局                            | 对局计入**当前等级场次**       | 已完成局数 `x` += 1                                          |
| 发奖机会 | 当前阶段 `x` >= 本阶段 `targetWins`（即界面 `y`），打开对局抽奖 | 系统结算本阶段任务            | 按配置发放抽奖券（张数见 `ticketPerComplete`）；本阶段剩余进度`x`-`y`继承至下一阶段 |
| 阶段解锁 | 上一阶段已至少完成一次完整循环（或满足配表声明的解锁条件）                | 系统推进                 | 解锁下一阶段；首阶段默认已解锁                                         |
| 末段循环 | 当前已是 `stages` 最后一项                           | 再次完成该阶段 `targetWins` | **不进入新阶段**，仍停留在该阶段；继续用该阶段 `targetWins` 与 `rewardPoolId` |
| 进度独立 | 切换场次                                         | 各 `roomCode` 独立统计    | 阶段、进度、机会数互不串联                                           |
| 每日重置 | 每日 0:00（服务器时间）                               | 系统自动重置               | 当日对局数清零；任务阶段重置                                          |

**进度示例：** R1 配置阶段 A：`targetWins=3`；B：`targetWins=7`；C：`targetWins=10`；D：`targetWins=10`（末段）。玩家完成 A 后解锁 B，…，进入 D 后每次再打满 10 局发一次机会，奖池始终用 D 绑定的 `rewardPoolId`。

## 5. 异常与边界处理

| **异常场景** | **前置条件**                  | **处理策略**                             | **补偿方式**         |
| -------- | ------------------------- | ------------------------------------ | ---------------- |
| 对局中断线    | 玩家在对局中断线                  | 若对局已结算则计入进度，未结算则不计入                  | 无需补偿             |

## 7. 配置设计

### 7.1 房间与多阶段任务配置（每场次独立）

**结构：** 共 **5 个场次档位**（`roomCode` = R1\~R5），**每个场次单独一条主配置**。每条主配置包含有序数组 `**stages**`，阶段标识为 **A、B、C、D …**（长度不限，顺序即解锁顺序）。

**场次级公共字段：**

| 字段             | 类型     | 说明                             | 示例值             |
| -------------- | ------ | ------------------------------ | --------------- |
| `roomCode`     | string | 场次代号 R1\~R5，唯一                 | `R1`            |
| `roomSwitch`   | int    | 场次开关 1=开 0=关                   | `1`             |
| `maxDrawCount` | int    | **该场次**当日使用抽奖机会的上限；999 表示近似无上限 | `100`           |
| `stages`       | array  | 有序阶段列表，见下表                     | `[{...},{...}]` |

**单个阶段** `**stages[i]**` **字段：**

| 字段                  | 类型     | 说明                             | 示例值         |
| ------------------- | ------ | ------------------------------ | ----------- |
| `stageCode`         | string | 阶段标识                           | `A`         |
| `order`             | int    | 同场次内顺序，从 1 递增                  | `1`         |
| `targetWins`        | int    | 本阶段需累计完成局数，即界面 `y`             | `7`         |
| `ticketPerComplete` | int    | 本阶段每完成一次循环发放的抽奖机会次数            | `1`         |
| `rewardPoolId`      | string | **本阶段抽奖**使用的奖池 ID（可与其它阶段相同或不同） | `R1_POOL_D` |

**解锁与循环（服务端逻辑约束）：**

1. **解锁：** `order=1` 的阶段默认解锁；`order=k`（k>1）仅当 `order=k-1` 阶段已至少完成**一次**完整循环后解锁（若有额外字段如 `unlockType`，以实现为准，但须在校验清单中覆盖）。
2. **循环：** 设 `stages` 共 N 条。当玩家当前阶段为第 N 条且再次完成 `targetWins` 后，**当前阶段索引仍为 N**，持续使用第 N 条的 `targetWins`、`ticketPerComplete` 与 `rewardPoolId`。

**与旧字段的对应关系（迁移）：** 原 `taskA/taskB/taskC` 可映射为 `stages` 前三项的 `targetWins`；扩展时继续追加 D、E 即可。

### 7.2 奖励池配置（阶段独立 · 多奖励类型）

**原则：** 奖池与 `**rewardPoolId**` 绑定。玩家在某阶段点击抽奖时，使用**该阶段**配置的 `rewardPoolId` 指向的奖池，从而实现「**每个阶段的任务奖励概率可分开配置**」。展示用格子与 `slots` 对齐（建议前 5 个主展示，多于 5 个滚动）。

**奖池表（每条** `**rewardPoolId**` **一条）：**

| 字段              | 类型     | 说明                                                           |
| --------------- | ------ | ------------------------------------------------------------ |
| `rewardPoolId`  | string | 唯一 ID，被 `stages[i].rewardPoolId` 引用                          |
| `slots`         | array  | 奖励档位列表，长度不限（客户端多则滚动）                                         |
| `slots[k].gift` | string | `类型*数量`，如 `Silver*1000`、`Card*1`、`PeekBottom*1`、`Exchange*5` |
| `slots[k].p`    | float  | 该档位中奖概率；按照奖励权重计算                                             |

**奖励类型枚举（可扩展）：**

| 道具id   | 名称     | 说明                            |
| ------ | ------ | ----------------------------- |
| 21330  | 银子     | 游戏内主货币                        |
| 50469  | 记牌器（局） | 对局辅助道具                        |
| 51597  | 看底牌    | 对局辅助道具（示例，实际上线以道具 ID / 计费点为准） |
| 50649  | 兑换券    | 商城兑换等                         |
| <br /> | 其它道具   | 按项目道具表扩展；配置校验须校验合法            |

**示例：** 阶段 A 使用 `R1_POOL_A`（偏新手：道具 权重高、银子 低）；末阶段 D 使用 `R1_POOL_D`（控制通胀：压低 银子、兑换券概率）。

### 7.3 获奖记录配置

| **字段**             | **类型** | **说明**          | **示例值** |
| ------------------ | ------ | --------------- | ------- |
| `recordMaxCount`   | int    | 获奖记录最大保留条数      | `50`    |
| `recordRetainDays` | int    | 记录保留天数（0=当期活动内） | `7`     |

记录会一直保留最大条数不会清空，不需要保留天数

### 7.4 配置校验清单

- **五场次独立：** R1\~R5 各有一条主配置，`roomCode` 与房间映射一致、无重复、无遗漏
- **阶段有序：** 每个场次内 `stages` 的 `order` 从 1 连续递增，`stageCode` 不重复
- **解锁链完整：** 除首阶段外，每阶段可推导解锁依赖（默认：上一阶段完成一次循环）
- **末段循环：** 最后一个 `stages` 元素之后无隐式新阶段；循环时仍绑定该阶段 `rewardPoolId`
- **局数合理：** 各阶段 `targetWins` > 0；`ticketPerComplete` ≥ 1
- **奖池引用有效：** 每个 `rewardPoolId` 均在奖池表中存在且被至少一个阶段引用
- **概率独立校验：** **每一个** `rewardPoolId` 内 无负值、无空池
- **高场次价值：** 对标同阶段或末段循环期望，高场次奖励期望 ≥ 低场次（无倒挂或已备注例外）
- `roomSwitch` 关闭的场次在客户端不展示
- 各场次 `maxDrawCount` 与经济投放预算匹配
- `slots[k].gift` 类型与数量合法
- 文案、主界面奖励展示与**当前阶段绑定奖池**一致

## 8. 数值方案

### 8.1 输入信息

| **维度** | **内容**                  |
| ------ | ----------------------- |
| 目标人群   | 新手/活跃/高付费 三层玩家          |
| 目标行为   | 提升日均对局数、次日留存、抽奖参与率      |
| 资源池    | 银子、记牌器、兑换券、抽奖券          |
| 调整对象   | 任务局数、概率、奖励数量、每日上限、抽奖券上限 |

### 8.2 设计逻辑

1. **按场次：** R1\~R5 **分别**维护 `stages` 与 `maxDrawCount`，不得共用一条配置行（可复用 `rewardPoolId`，但阶段行须各自引用）。
2. **按阶段：** 阶段数可为 A\~D 或更多；**完成前置阶段一次完整循环**后解锁下一阶段。
3. **末段循环：** 玩家处于最后一个 `stages` 元素时，只重复该阶段的局数目标与奖池。
4. **按奖池：** 每个阶段通过 `rewardPoolId` 指向独立 `slots` 与概率；**阶段之间概率互不影响**，概率通过各奖励权重得出
5. **奖励类型：** 不限于银子；记牌器、看底牌、兑换券等均在 `slots[k].gift` 中配置。

### 8.3 三档数值方案（参数模板 + R1 / R5 示例）

下列 **保守 / 标准 / 激进** 三档，表示**同一套结构下的推荐取值区间**；落地时写入各场次 `stages` 与奖池表即可。表中 `targetWins(A…D)` 表示该档下「若配置四阶段」时各阶段建议局数（若只配三阶段则去掉 D 行即可）。

#### 8.3.1 全档位通用参数（模板）

| 参数含义                       | 保守     | 标准    | 激进   |
| -------------------------- | ------ | ----- | ---- |
| 阶段数（建议）                    | 3\~4   | 4     | 4\~5 |
| 首阶段 `targetWins`（A）        | 5      | 3     | 2    |
| 末前阶段 `targetWins`（C 或倒数第二） | 12\~15 | 8\~10 | 5\~8 |
| 末阶段 `targetWins`（循环段 D）    | 15     | 10    | 6\~8 |
| `maxDrawCount`（R1 参考）      | 50     | 100   | 200  |
| `maxDrawCount`（R5 参考）      | 30     | 50    | 100  |

支持按等级房间设置新用户首次任务所需局数；完成新手任务后自动衔接所配置对应房间下的任务完成一次后失效；

新手任务不做完不重置进度至多保留3个月；

#### 8.3.2 R1（初级场）示例 — 四阶段 + 分池概率（标准档示意）

**任务（**`**stages**`**，每条** `**ticketPerComplete=1**`**）：**

| 阶段 | `stageCode` | `targetWins` | `rewardPoolId`  |
| -- | ----------- | ------------ | --------------- |
| 1  | A           | 3            | `R1_STD_POOL_A` |
| 2  | B           | 7            | `R1_STD_POOL_B` |
| 3  | C           | 10           | `R1_STD_POOL_C` |
| 4  | D（末段，循环）    | 10           | `R1_STD_POOL_D` |

**奖池概率（每个池独立 ∑p=100%，数值为示意）：**

| 奖池 ID                   | 银子\*1000 | 记牌器\*1 | 看底牌\*1 | 兑换券\*1 |
| ----------------------- | -------- | ------ | ------ | ------ |
| `R1_STD_POOL_A`         | 55       | 25     | 5      | 15     |
| `R1_STD_POOL_B`         | 45       | 30     | 10     | 15     |
| `R1_STD_POOL_C`         | 40       | 28     | 12     | 20     |
| `R1_STD_POOL_D`（循环期控通胀） | 35       | 25     | 15     | 25     |

**保守档调整方向：** A 的 `targetWins` 略增、各池 Silver 权重略降、末池礼券概率略降。**激进档：** A 局数更小、末池 Silver 权重更高（需配合更低 `maxDrawCount` 或更严监控）。

#### 8.3.3 R5（宗师场）示例 — 四阶段 + 分池概率（标准档示意）

**任务：**

### 8.4 数值必查项

- 各场次末段循环奖池的**期望价值**与投放节奏是否可接受（配合 `maxDrawCount`）
- 权重可配置为0
- 高场次同阶段或末段期望 ≥ 低场次
- `targetWins` 与解锁节奏：新手是否在 A 段过难 / 过易
- 记牌器、看底牌、礼券等是否对商城付费造成挤压（分池单独评审）

## 9. 经济影响评审

### 9.1 经济影响结论

| **维度** | **评估**              |
| ------ | ------------------- |
| 风险等级   | 中                   |
| 影响周期   | 中期（上线后 1\~2 周需持续观测） |

### 9.2 评审维度分析

| **维度** | **分析**                     |
| ------ | -------------------------- |
| 资源产出   | 新增对局抽奖产出通道，银子/道具/兑换券三类均有增量 |
| 资源消耗   | 新增抽奖券消耗环节，抽奖券本身不可交易，消耗路径单一 |
| 循环速度   | 产出增长快于消耗增长，需关注银子库存膨胀       |
| 玩家分层   | 高场次玩家单次奖励价值高，有放大马太效应风险     |

### 9.3 关键风险点

| **风险**          | **等级** | **影响**         |
| --------------- | ------ | -------------- |
| 银子投放超预期导致通胀     | 高      | 成本控制难，新手体验恶化   |
| 礼券投放挤压商城付费点     | 中      | 降低直充转化率        |
| 记牌器投放过多削弱道具付费价值 | 中      | 付费记牌器 ARPPU 下降 |
| 高场次玩家产出远超低场次    | 低      | 马太效应加剧         |
| 抽奖券囤积后集中使用      | 低      | 可能造成短期奖励集中发放   |

### 9.4 调整建议

**立即执行：**

- 设置每日银子总投放上限告警阈值
- R4/R5 的高价值奖励采用低概率 + 分段门槛
- 设置合理的 `ticketLimit` 防止过度囤券

**观察后执行：**

- 上线 1 周后对比银子产消比变化，若产出增幅 > 15% 则下调 B/C 段银子奖励
- 若兑换券兑换率异常上升，收紧兑换券投放概率
- 观察抽奖券囤积行为，必要时缩短券的有效期

## 10. 埋点方案

### 10.1 命名规则

采用统一命名格式：`对局抽奖_场景_动作`

动作词统一规范：

- 展示类：`显示成功`
- 交互类：`点击`、`关闭`
- 结果类：`成功`、`失败`
- 特殊类：`重复点击`

### 10.3 漏斗覆盖检查

**主漏斗：**  入口曝光() → 入口点击() → 界面到达() → 抽奖点击() → 抽奖成功() → 奖励到账()

| **漏斗节点** | **覆盖状态** |
| -------- | -------- |
| 展示       | ✓        |
| 点击入口     | ✓        |
| 到达界面     | ✓        |
| 触发行为     | ✓        |
| 行为结果（成功） | ✓        |
| 行为结果（失败） | ✓        |
| 发奖结果     | ✓        |

**辅助漏斗（获奖记录）：**  获奖记录点击() → 获奖记录展示()

**辅助漏斗（道具背包）：**  我的抽奖券点击() → 道具背包展示()

**抽奖券获取链路：**  对局完成 → 抽奖券获得()

**链路完整性：** 完整

### 10.4 风险与建议

- 命名冲突：新增事件名前需与现有埋点表查重，确认 【】～【】 段无占用
- 缺失节点：当前链路完整，无缺失
