# 高级场开局失败故障分析

## 问题描述

### 现象
- 四个房间（初级场 ×2、中级场、高级场）共用同一 roomsvr 进程（`roomsvrxzmo`）
- 高级场（银币/金币场）周期性地（约 1 个月）出现**所有桌子无法开局**
- 四个玩家凑齐后点开始，无任何反应，没有错误提示
- 一旦出现，持续存在，直到**重启 roomsvr 进程**才能恢复
- 其他三个房间的对局完全正常
- 进程不崩溃，无相关错误日志

### 环境参数
- 高级场活跃桌子数：**13 张**（非 300 张全用）
- 房间类型：roomtype=3（高级场）
- 通信方式：roomsvr → `.tmp` 文件 + `PostMessage` → gamesvr
- 房间服务进程与游戏服务进程是独立的两个进程

---

## 架构与流程

### 进程关系

```
roomsvr (port 30629)                  gamesvr
    │                                    │
    │ 1. 写入 .tmp 文件                   │
    │ 2. PostMessage 通知                 │
    │ ────────────────────────────────>  │
    │                                    │ 3. 读取 .tmp 文件
    │                                    │ 4. StartSoloTable()
    │ <────────────────────────────────  │
    │   5. PostCloseSoloTable (失败时)    │
```

### 开局链路

```
玩家凑齐4人 → OnAskNewTable()
  → GetRandomPosition()    分配随机桌子
  → SetRandomPosition()    入座（nPlayerCount++）
  → IsFullTable()          检查 4人已满？
    → TRUE: SendRandomPlaying() → CommitTPS(PLAYING) → PostStartSoloTable()
    → FALSE: 静默返回，不开局，不打日志
```

## 已排除的猜想

### 猜想 1：PostMessage 消息队列溢出

**提出原因**：`PostMessage` 有 10000 条上限。

**排除理由**：用户提供了实际流量数据（160 人同时在线，3-7 分钟一局），消息率约 0.22 开局消息/秒，总计约 44 条消息/秒，远未达到队列上限。且不可能只影响一个房间。

---

### 猜想 2：GetFreeTableNO 表耗尽（-1 返回）

**提出原因**：[roomOpenData.cpp:965](d:/LibraryVC12_P/RoomOpen/trunk/roomOpenData.cpp#L965) 中 `GetFreeTableNO` 返回 -1 时，`m_mapTable.Lookup(-1, pNewTable)` 拿到未初始化指针，后续 `MoveRandomTable` 写向垃圾地址。

**排除理由**：高级场实际只使用 13 张表，还有 287 张空闲。不可能表耗尽。这是一个真实存在的 Bug，但并非此次故障的根因。

---

### 猜想 3：.tmp 文件路径不匹配（roomsvr vs gamesvr）

**提出原因**：roomsvr 的 `GetGameSvrFolder()` 从 `yxpdsvr.ini` 的 `SVRPATH\[nGamePort]` 读路径，gamesvr 的 `OnStartSoloTableSync` 用 `GetModuleFileName` 取自己路径。如果两者不同，gamesvr 找不到 `.tmp` 文件。

**排除理由**：如果路径不匹配，所有房间都会立即出问题，而不是只影响高级场且需要一个月。

---

### 猜想 4：横跨四个房间的桌子编号冲突

**提出原因**：四个房间都写 `.tmp` 到同一目录，如果文件名不含 roomID，不同房间的相同 tableNO 会互相覆盖。

**排除理由**：[文件名格式是 `solo\%d_%d.tmp`](d:/LibraryVC12_P/RoomOpen/trunk/roomOpenData.cpp#L1102)，参数为 `roomID` 和 `tableNO`。每个房间的文件独立，不存在冲突。

---

### 猜想 5：机器人配置导致的问题

**提出原因**：`roomsvrxzmo.ini` 中有 `[Robot]` 配置。

**排除理由**：用户确认**只有初级场配置了机器人**，高级场无机器人。且问题现象与机器人行为无关。

---

## 已确认的 Bug（按严重程度排序）

### Bug 1（致命）：SetRandomPosition 先自增 nPlayerCount 再检查座位碰撞

**位置**：[roomdata.cpp:1364-1385](d:/LibraryVC12_P/RoomBasic/trunk/roomdata.cpp#L1364-L1385)

```cpp
void CBaseRoomData::SetRandomPosition(PLAYER* pPlayer, TABLE* pTable, PLAYER_POSITION* pp)
{
    pPlayer->pe.nRandomTableNO = pp->nTableNO;
    pPlayer->pe.nRandomChairNO = pp->nChairNO;
    pPlayer->pe.nEnterTime = GetTickCount();

    if(pTable->th.nPlayerCount == 0)
        pTable->nFirstStartTime = GetTickCount();
    pTable->th.nPlayerCount++;    // ← 无论如何都自增

    if(pTable->nPlayerAry[pp->nChairNO] != 0)  // 座位被占？
    {
        LOG_WARN("=========== SetRandom Position,tab:%d chair[%d]=%d=============",
            pTable->th.nTableNO, pp->nChairNO, pTable->nPlayerAry[pp->nChairNO]);
        pp->nChairNO = GetFreeChairNO(pTable);  // 换空位
    }

    pTable->nPlayerAry[pp->nChairNO] = pp->nUserID;
    // ← 被碰撞的老座位在 nPlayerAry 中未被清除！
}
```

**问题**：
1. `nPlayerCount++` 在座位碰撞检查**之前**执行
2. 碰撞后虽然换到了空位，但被碰撞座位的 `nPlayerAry` 旧条目**从未清理**
3. 这张桌子的 `nPlayerAry` 里实际存活的非零条目数 > `nPlayerCount`

**后果**：成百上千局游戏后，`nPlayerAry` 中累积的废弃条目越来越多。结合 `MoveRandomTable` 的全量拷贝，污染在表之间传播。最终 `nPlayerCount > nChairCount`，`IsFullTable` 永远返回 FALSE。

**位置**：[roomOpenData.cpp:1104-1107](d:/LibraryVC12_P/RoomOpen/trunk/roomOpenData.cpp#L1104-L1107)

## 核心根因假设

### 级联失效机制

上述 Bug 1（致命）和 Bug 2（高）共同构成了最可能的故障链路：

**阶段 1 — 幽灵条目积累**

`SetRandomPosition`（Bug 1）每次座位碰撞都在 `nPlayerAry` 中留下一个废弃条目。这些条目不被清除，随游戏局数持续积累。

**阶段 2 — 污染扩散**

`MoveRandomTable` 用 `memcpy` 全量拷贝 TABLE 结构，废弃的 `nPlayerAry` 条目随之传播到新表。

**阶段 3 — 表中状态死锁**

`StartSoloTable` 某些失败路径（Bug 2）不通知 roomsvr 清理，导致桌子永久卡在 `PLAYING` 状态。

**阶段 4 — 计数器越界**

`nPlayerCount` 因废弃条目和未清理状态的累积，最终 > `nChairCount`（4）。`IsFullTable(nPCnt > 4 == 4)` 永远为 FALSE。

### 为什么约一个月复现

- 高级场活跃表数 13 张
- Bug 2 每次触发损失 1 张表（几个月逐渐卡死）
- Bug 1 导致 nPlayerCount 膨胀在所有 13 张表上同步累积
- 二者叠加 → ~1 个月后全部 13 张表无法开局

### 为什么只影响高级场

- 不同场次的 `FixBaseSilver`、`feeratiotobasedeposit` 等阈值不同
- `CheckBeforeGameStart` 的校验逻辑可能对高级场（高额银币）更敏感
- 非房卡房间（银币/金币场）的清理路径（`IsNeedRoomCard()` 检查）跳过了玩家移除逻辑

### 为什么重启恢复

所有状态在 roomsvr 进程内存中。重启后 `m_mapTable` 重新初始化，全部清零，回到正常状态。
